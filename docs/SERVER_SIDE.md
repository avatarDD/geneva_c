# Server-side: стратегии на сервере и `geneva agent`

Стратегии Geneva бывают не только клиентские. Server-side стратегия
работает на сервере и меняет его пакеты (SYN+ACK, ответы), а клиенту
ничего ставить не нужно. Так Geneva обходила цензоры Китая, Индии и
Казахстана (`geneva library --server-side`).

Проверить такую стратегию можно только соединением из цензурируемой сети.
Поэтому оценка делится на две части:

```
geneva agent  (в цензурируемой сети:          geneva eval/evolve --agent  (на сервере, root:
роутер или ПК, без прав)                      движок на порту сервиса)
        <──────── запрос пробы: {"cmd":"probe",...} ────────
        ───────── соединение с сервисом ──────────────────>  стратегия меняет пакеты сервиса
        ───────── {"outcome":"ok","fitness":400,...} ──────>
```

На сервере работают сервис (веб-сервер, DNS и т.п.) и `geneva eval` или
`geneva evolve`. Движок ставит стратегию на порт сервиса (`--port`), а
агент по запросу подключается к сервису и сообщает результат. Пробы те же,
что у клиентской оценки (`docs/EVAL.md`): `http`, `tls`, `dns`, `tcp`.
Пробы `exec` и `external` агент не выполняет: он только открывает сетевые
соединения.

## Запуск

Агент слушает, сервер подключается к нему:

```
# в цензурируемой сети
geneva agent --listen tcp:0.0.0.0:7110 --token SECRET
# на сервере 203.0.113.5 с веб-сервером на порту 80
sudo geneva evolve --agent tcp:198.51.100.7:7110 --agent-token SECRET \
    --probe http --host example.com --ip 203.0.113.5 --port 80 --bad-word ultrasurf
```

Агент за NAT (роутер дома) сам подключается к серверу:

```
# на сервере: ждёт агента до --agent-wait секунд (по умолчанию 300)
sudo geneva evolve --agent-listen tcp:0.0.0.0:7111 --agent-token SECRET \
    --probe http --host example.com --ip 203.0.113.5 --port 80
# в цензурируемой сети
geneva agent --connect tcp:203.0.113.5:7111 --token SECRET
```

`--ip` — адрес сервера, каким его видит агент. Если задан только `--host`,
адрес определяет сервер и передаёт агенту, чтобы агент не спрашивал
цензурируемый DNS. Токен можно задать переменными `GENEVA_AGENT_TOKEN` (и
у агента, и у сервера), чтобы он не был виден в списке процессов.

Если соединение с агентом рвётся, сервер подключается заново (или ждёт,
пока агент подключится сам) и повторяет пробу один раз. Агент в режиме
`--connect` переподключается каждые `--retry` секунд.

## Ограничения

- Одна стратегия за раз (`--workers 1`): у сервиса один порт, и стратегия
  действует на все его соединения. Это касается и чужих клиентов
  сервиса, поэтому подбор лучше вести на отдельном порту или сервере.
- Агент выполняет одну пробу за раз. Таймаут пробы — не больше 60 с,
  ответ — не больше 16 МБ.
- Агент на адресе не из loopback (и любой `--connect`) требует токен.
  Неверный токен закрывает соединение. Канал не шифруется: используйте
  длинный случайный токен, а для чувствительных случаев туннель (SSH,
  WireGuard).
- Агенту не нужны права и движок. Он работает на роутере (OpenWrt,
  Entware), Linux и Windows.

## Протокол

Протокол — тот же, что у управляющего сокета (`docs/PROTOCOL.md`): JSON
по строкам. Сервер всегда начинает с `auth`, затем `hello`:

```
-> {"id":1,"cmd":"auth","token":"SECRET"}
<- {"id":1,"ok":true}
-> {"id":2,"cmd":"hello"}
<- {"id":2,"ok":true,"version":"0.9.0","proto":1,"os":"linux","arch":"mipsel","probes_run":0,"probes":["http","tls","dns","tcp"]}
-> {"id":3,"cmd":"probe","probe":{"kind":"http","host":"example.com","ip":"203.0.113.5","port":80,"timeout":5,"path":"/","bad_word":"ultrasurf"}}
<- {"id":3,"ok":true,"outcome":"ok","fitness":400,"bytes":1256,"detail":"HTTP 200, 1256 bytes"}
```

Поля `probe`: `kind`, `host`, `ip`, `port`, `timeout`, `path`, `bad_word`,
`valid_contains`, `injected_contains`, `min_bytes`, `max_bytes`,
`tls_version` (12, 13 или 0), `alpn`, `dns_tcp`, `dns_aaaa`, `dns_expect`,
`dns_bad`, `payload` (`hex:...`). Значения те же, что у одноимённых ключей
`geneva eval`. Отказ (`ok:false`) останавливает оценку: тот же запрос
снова не пройдёт.

События агента (`--events`): `start` (`mode: "agent"`), `ready`,
`connected` и `disconnected` (режим `--connect`), `exit` (`probes`).

## Проверка на стенде

`tests/e2e/censors.sh build/geneva server`: агент в namespace клиента,
`geneva eval --agent` в namespace сервера, цензоры на роутере между ними.
Проверяется, что стратегия на порту сервиса действует, неверный токен не
принимается, а server-side стратегии обходят лабораторных цензоров:

| Стратегия (на сервере) | Обходит цензоры |
|---|---|
| `[TCP:flags:SA]-duplicate(tamper{TCP:flags:replace:S}(tamper{TCP:chksum:corrupt},),)-\| \/` | 1, 2, 3, 5 |
| `[TCP:flags:SA]-duplicate(tamper{TCP:flags:replace:R}(tamper{TCP:chksum:corrupt},),)-\| \/` | 6, 7 |

Первая перед SYN+ACK шлёт SYN с испорченной суммой: цензор
синхронизируется по нему на чужой `seq`, а клиент его отбрасывает. Вторая
шлёт такой же RST, и цензор забывает соединение.

Затем `geneva evolve` на сервере сам находит обход цензора 2. Триггер
закреплён на SYN+ACK (`--fix-trigger TCP:flags:SA`), как в server-side
экспериментах Geneva, а поля ограничены (`--fields
flags,seq,ack,chksum,window`): подбор ищет, что сделать с SYN+ACK. Обычно находится
«одновременное открытие» (`[TCP:flags:SA]-tamper{TCP:flags:replace:S}-|`):
сервер отвечает SYN вместо SYN+ACK, клиент принимает это по правилам TCP,
а цензор синхронизируется на `seq` сервера. Другая находка — маленькое
окно в SYN+ACK (`[TCP:flags:SA]-tamper{TCP:window:replace:20}-|`):
клиент режет запрос на сегменты по 20 байт, и запрещённое слово не
попадает целиком ни в один пакет. Без закреплённого триггера
пространство поиска намного шире, и нужны популяция и число поколений
побольше. Отдельно проверяется агент, который подключается сам
(`--connect`).
